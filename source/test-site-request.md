# 공공 웹사이트 불법광고 탐지 테스트 사이트 제작 요청

## 1. 목적 및 공통 원칙

우리 팀은 「공공 웹사이트 불법광고 탐지 도구 개발 공모전」에 참가하며, 개발 중인 탐지 프로그램을 검증할 테스트 웹사이트가 필요하다.

첨부한 모집요강을 먼저 분석하고, 아래 요구사항에 맞는 사이트를 실제로 구현하라. 기획안 제시만으로 끝내지 말고 실행 가능한 파일, 검증실, 정답표, 사용 설명서를 제공하라.

### 1.1 제작 목적

탐지 프로그램에 진입 URL 하나를 입력했을 때 다음 과정을 검증할 수 있어야 한다.

- 내부 링크를 따라 하위 페이지와 게시글을 발견하는가?
- 본문·댓글·동적 DOM·iframe에서 분석 대상 요소를 누락 없이 수집하는가?
- 원문, 속성, 스타일, 위치, 선택자, 프레임 경로를 정확히 수집하는가?
- 불법광고의 은닉·위장 기법을 분류하는가?
- 정상 콘텐츠를 불법광고로 오인하지 않는가?
- 규격에 맞는 `result.json`을 생성하는가?

공식 심사 사이트는 비공개다. 따라서 결과물을 “모집요강 기반 모의 테스트 환경”으로 명시하고, 실제 심사 사이트와 동일하다고 주장하지 않는다.

### 1.2 구현 원칙

- 정적 호스팅에 배포 가능한 프론트엔드 사이트로 구현한다.
- HTML·CSS·JavaScript를 기본으로 사용한다. 프레임워크를 쓰더라도 최종 결과물은 정적 배포가 가능해야 한다.
- 여러 페이지, 실제 `a href`, 게시판 목록과 페이지네이션을 포함한다.
- 특정 개발 서버의 경로 재작성 기능에 의존하지 않는다.
- 외부 API·데이터베이스·로그인 없이 작동해야 한다.
- 동적 콘텐츠는 브라우저의 JavaScript로 생성한다.
- 루트 경로와 하위 경로 배포에서 링크·자산·iframe이 정상 동작해야 한다.
- 데스크톱과 모바일에서 사용할 수 있도록 제작한다.
- 실제 기관을 사칭하지 않는 가상의 기관명과 합성 콘텐츠를 사용한다.
- 실제 거래·결제·연락 기능은 넣지 않는다. 외부 링크 시험에는 `.invalid` 등 비연결 주소를 사용한다.
- 대상 페이지의 제목·클래스·ID 등에 정답 기법이나 정답 여부를 노출하지 않는다.

### 1.3 공통 필수 탐지 범위

아래 4종을 모두 포함한다. 분류는 첨부 모집요강을 우선한다.

| 코드 | 포함할 사례 |
| --- | --- |
| HOMOGLYPH | 전각·키릴 등 닮은꼴 문자, 숫자 치환 |
| JAMO | 호환 자모, 조합 자모, 일부 음절 분해 |
| TRANSPARENT | 투명 글자, opacity:0, 배경색과 같은 글자색, 부모 스타일의 영향 |
| OFFSCREEN | 음수 좌표, font-size:0~1px, display:none, 부모 요소에 의한 은닉 |

같은 요소에 여러 기법을 적용하는 사례도 포함한다. 이때 정답은 기법별로 각각 한 건이다.

접근성 텍스트, 숨겨진 정상 메뉴, 한글 교육 자료, 전각 정상 표기, 불법광고 예방 안내 등의 정상 대조 사례를 함께 넣는다.

30분은 탐지 실행의 상한이지 목표 소요시간이 아니다. 긴 대기나 무한 페이지로 시간을 소모시키지 말고, 수집·분류·위치 식별·중복 제거를 어렵게 만드는 방식으로 난이도를 높인다.

첨부 문서와 이 요청이 충돌하면 충돌 지점을 설명한다. 문서에 없는 심사 조건이나 점수 산식을 임의로 만들어 공식 기준처럼 표현하지 않는다.

## 2. 이번 사이트의 제작 명세

아래 설정을 이번 사이트의 요구사항으로 사용하라.

### 2.1 이름과 콘셉트

- 사이트 식별자: `[예: hanbit-civic]`
- 가상 기관명: `[예: 한빛시]`
- 사이트 콘셉트: `[예: 지자체 시민소통광장]`
- 주요 이용자: `[예: 생활정보를 찾고 의견을 나누는 시민]`
- 디자인 방향: `[예: 실제 공공기관 게시판처럼 단정하고 정보 밀도가 높은 화면]`
- 주요 색상: `[예: 네이비·민트·화이트]`

### 2.2 페이지 구성과 규모

- 주요 영역: `[예: 메인, 자유게시판, 공지사항, 생활정보, 문화행사, 아카이브]`
- 게시글·콘텐츠 시나리오 수: `[예: 47개]`
- 광고 포함 시나리오 수: `[예: 35개]`
- 정상 대조 시나리오 수: `[예: 12개]`
- 목록 페이지당 항목 수: `[예: 12개]`
- 목표 탐색 깊이: `[예: 시작 페이지에서 링크를 5번 따라가야 발견되는 사례 포함]`

여기서 시나리오 수는 서로 구분되는 게시글·콘텐츠의 수다. 공통 메뉴, 목록, 검증실, iframe 보조 문서 수와 구분해 보고하라.

기대 검출 건수는 광고 요소와 중첩 기법 구성으로부터 자동 산출하라. 광고 포함 시나리오 수와 같다고 가정하지 않는다.

### 2.3 콘텐츠 구성

- 정상 콘텐츠 주제: `[예: 지역 행사, 도서관, 산책로, 시민 제안]`
- 합성 광고 주제: `[예: 도박·성인물 중심, 불법 대출·의약품 판매 일부]`
- 광고 삽입 영역: `[예: 본문, 댓글, 이웃 소식 위젯, 이전 게시글]`
- 정상 사례 비중과 특징: `[예: 예방 안내와 접근성 콘텐츠를 충분히 포함]`

화면에는 실제로 있을 법한 제목·작성자·날짜·본문을 사용한다. 사례 이름을 그대로 게시글 제목으로 쓰지 않는다.

### 2.4 난이도와 중점 시험 요소

- 난이도: `[기본 / 중급 / 고급]`
- iframe: `[예: 동일 출처 1·2단계, 지연 생성 iframe 포함]`
- 동적 삽입: `[예: 650ms·1600ms·2800ms 후 댓글 추가]`
- URL 시험: `[예: 쿼리 값별 본문 분기, 파라미터 순서 변경, fragment 중복]`
- 위치 식별: `[예: 반복 클래스, 클래스 없는 요소, 깊은 중첩 구조]`
- 복합 기법: `[예: HOMOGLYPH+TRANSPARENT, JAMO+OFFSCREEN]`
- 추가 중점 사항: `[예: 부모 스타일 때문에 숨겨지는 자식 요소 수집]`

무작위 광고 교체나 실행마다 달라지는 정답은 사용하지 않는다. 모든 지연과 콘텐츠는 재현 가능해야 한다.

### 2.5 배포 범위

- 프로젝트 디렉터리: `source/test-site-N/` (기관명 대신 사이트 번호 사용)
- 탐지 대상 배포 디렉터리: `test-site-N/`
- 공통 결과 대시보드: `validator/?site=N`
- 사이트별 상세 검증실: `source/test-site-N/lab/`

- 이번 요청의 배포 범위: `[로컬 실행 및 배포용 파일 준비 / 지정 서비스에 실제 배포]`
- 지정 배포 서비스: `[없음 또는 서비스명]`

실제 배포를 완료하지 못하면 로컬 실행과 배포 완료를 구분해 설명한다.

## 3. 검증실 및 산출물 규격

각 팀원이 만든 사이트를 같은 방식으로 시험할 수 있도록 아래 구조와 동작을 유지하라.

### 3.1 대상 사이트와 검증실 분리

저장소에서는 공통 대시보드 `validator/`를 주 결과 비교 화면으로 사용하고, 사이트별 `source/test-site-N/lab/`은 정답 사례·DOM 검사를 유지하고 사이트 2 이상의 기존 링크 검사도 보존한다. 대시보드는 source/sites.json을 읽고 같은 출처의 기존 검증실 Promise API를 사용한다. 아래 /lab 경로는 단독 생성물 tmp/build/test-site-N/ 기준이며, 저장소 정답은 각 reference/에 둔다.

- `/index.html`: 탐지기에 입력할 시작 페이지
- `/lab/index.html`: 사람이 사용하는 검증실
- `/lab/manifest.json`: 검증실용 정답 데이터
- `reference/ground-truth.json`: 보관용 정답 데이터

대상 페이지에서는 검증실이나 정답표로 연결되는 링크를 제공하지 않는다. 모든 탐지 대상은 시작 페이지의 내부 링크와 iframe을 통해 도달할 수 있어야 한다.

iframe 문서를 독립 페이지로 재탐색해 정답 수가 중복되지 않도록 시험 범위를 문서화한다. 공통 정답표에서는 부모 페이지 URL과 iframe 경로를 사용한다.

검증실 분리는 접근 제어가 아니다. 정답 비공개 배포가 필요할 때는 `lab/`을 제외할 수 있도록 안내한다.

### 3.2 정답표 형식

정답표는 다음 구조를 사용한다. 경로는 배포 기준 경로에 대한 상대경로로 저장한다.

```json
{
  "version": "1.0.0",
  "siteId": "사이트-식별자",
  "entry": "index.html",
  "fixtureViewport": {
    "width": 1440,
    "height": 1000
  },
  "maxInjectionDelayMs": 2800,
  "cases": [
    {
      "caseId": "T01",
      "page": "board/posts/1047.html",
      "name": "전각 문자와 투명 스타일",
      "selector": "div.article-body > p.excerpt",
      "frames": [],
      "text": "실제 DOM에 들어 있는 정규화 전 원문",
      "techniques": ["HOMOGLYPH", "TRANSPARENT"],
      "delayMs": 0
    }
  ],
  "negativeControls": [
    {
      "caseId": "N01",
      "page": "board/posts/2001.html",
      "name": "숨겨진 정상 안내",
      "selector": "div.article-body > p.guide",
      "frames": [],
      "text": "정상 안내 원문",
      "techniques": [],
      "delayMs": 0
    }
  ]
}
```

프레임 내부 사례는 바깥쪽부터 순서대로 기록한다.

```json
"frames": [
  {
    "src": "widgets/outer.html",
    "selector": "iframe.community-widget"
  },
  {
    "src": "widgets/inner.html",
    "selector": "iframe.detail-widget"
  }
]
```

`selector`는 마지막 프레임 문서 안에서 해당 요소 하나만 가리켜야 한다.

한 페이지에 여러 정답 요소가 있으면 사례를 나누어 기록한다. 이 경우 페이지 수는 `page`의 고유 개수로 계산하고, 정답 요소 수와 구분한다.

### 3.3 검증실의 공통 기능

공통 대시보드는 사이트 자동/명시적 선택, 주소 불일치 안내, 파일 선택 전·읽기·비교·완료·오류 상태, TP/FN/FP/필드 오류/중복 요약, 기대값·제출값·이유 상세와 필터·검색을 제공한다. 기존 검증실을 1440×1000 동일 출처 iframe으로 실행하고 구조화 결과를 받으며, 판정 로직을 복제하거나 결과 HTML을 분석하지 않는다.

다음 기능을 모두 구현한다.

1. 사이트 이름·버전·진입 URL 표시 및 주소 복사
2. 대상 페이지 수, 정답 요소 수, 기대 검출 건수, 정상 대조 수 표시
3. 전체·기법별·정상 사례 필터와 사례 검색
4. 사례별 대상 페이지, 원문, 선택자, iframe 경로, 생성 지연 확인
5. `ground-truth.json` 다운로드
6. 현재 배포 주소를 반영한 `expected-result.json` 다운로드
7. 정답 요소 자체 검증
8. 팀 탐지기의 `result.json`을 선택해 결과 비교

UI 명칭과 주요 동작은 사이트마다 유지한다. 기관명·색상·콘텐츠는 2번 설정에 맞춰 변경할 수 있다.

### 3.4 정답 요소 자체 검증

실제 브라우저 DOM을 기준으로 확인한다.

- 대상 페이지와 iframe이 정상 로딩되는가?
- 지연 요소가 정해진 시점 이후 생성되는가?
- 선택자가 요소 하나만 가리키는가?
- 원문이 정답표와 정확히 일치하는가?
- TRANSPARENT/OFFSCREEN의 스타일이 요소와 조상에서 실제로 재현되는가?
- 정상 대조 사례도 정해진 위치에 존재하는가?

검증 성공·실패와 실패 이유를 사례별로 표시한다.

정답 요소를 직접 여는 검사와 별개로, 시작 URL에서 링크를 따라 모든 사례에 도달할 수 있는지도 확인한다. 고립된 페이지를 정답표에 넣지 않는다.

이 기능은 사이트 자체 검사다. 탐지 프로그램의 성능 측정이라고 표시하지 않는다.

### 3.5 예상 결과 파일

`expected-result.json`은 모집요강의 필수 구조를 따른다.

```json
{
  "meta": {
    "topic": "TOPIC",
    "entry_url": "현재 사이트의 전체 진입 URL",
    "started_at": "ISO 8601 시각",
    "finished_at": "ISO 8601 시각",
    "elapsed_sec": 0,
    "tool_version": "reference-1.0.0"
  },
  "findings": [
    {
      "id": "T01_HOMOGLYPH",
      "url": "해당 부모 페이지의 전체 URL",
      "is_violation": true,
      "location": "div.article-body > p.excerpt",
      "evidence_text": "정규화 전 원문",
      "technique": "HOMOGLYPH"
    }
  ]
}
```

- 하나의 `technique`에는 코드 하나만 기록한다.
- 복합 기법은 같은 위치에 대해 기법별 객체를 만든다.
- 정상 대조 사례는 findings에 넣지 않는다.
- iframe 위치는 절대 src와 ` >>> `로 연결한다.
- UTF-8 BOM 없는 JSON으로 내려받는다.
- 실행 시간 0초는 합성 예시임을 표시하고 실제 측정값으로 설명하지 않는다.

### 3.6 탐지 결과 비교

사용자가 선택한 파일은 브라우저 안에서 처리하며 외부로 전송하지 않는다.

다음을 검사한다.

- JSON 파싱, UTF-8 BOM, 필수 객체·필드·타입
- 고유 ID, 전체 URL, 허용된 기법 코드
- URL + 실제 요소 위치 + 기법의 일치
- 동일 검출의 중복
- 모호하거나 존재하지 않는 선택자

URL 비교에서는 쿼리 값을 보존한다. 파라미터 순서와 fragment는 중복으로 처리하고, 모집요강의 http/https 및 끝 슬래시 비교 규칙을 반영한다.

선택자는 문자열 일치만으로 판정하지 않는다. 작성 방식이 달라도 실제로 같은 요소 하나를 가리키면 인정한다. iframe의 상대 src와 결과의 절대 src도 올바르게 대응시킨다.

원문은 필수 필드로 확인하되, 모집요강에 따라 원문 문자열 차이만으로 위치·기법 정답을 오답 처리하지 않는다.

다음 결과를 표시한다.

- TP: 정탐
- FN: 미탐
- FP: 오탐
- 필수 필드 오류 수
- 통합한 중복 수
- 재현율: `TP / 전체 기대 검출 건수`
- 정밀도: `TP / (TP + FP)`
- 필드 오류 반영 비율: `TP / (TP + FP + 필드 오류 수)` (기존 검증실의 자체 정탐 비율)
- 제출 파일에 기록된 실행 시간과 1,800초 초과 여부

FN과 필드 오류는 같은 원인에서 함께 생길 수 있으므로 단일 실패 합계로 더하지 않는다. 중복은 별도 통합 정보다. 파일 전체 거부는 지표 없이 오류를 표시하며 TP0/FN전체로 바꾸지 않는다.

분모가 0이면 계산 불가로 표시한다. 이 비율은 팀 내부 비교용이며 공식 점수와 구분한다. 공개되지 않은 100점 환산식을 임의로 만들지 않는다.

### 3.7 검증실 자체의 테스트

완성 후 최소한 다음 입력으로 비교 기능을 시험하라.

- 완전한 정답 파일
- 일부 정답이 빠진 파일
- 정상 요소를 불법광고로 표시한 파일
- 같은 검출이 중복된 파일
- 동일 요소를 다른 CSS 선택자로 표시한 파일
- 여러 요소와 일치하는 모호한 선택자
- 필수 필드가 빠진 파일
- 잘못된 JSON 및 BOM 포함 파일

각 시험의 예상 결과와 실제 결과를 기록한다.

### 3.8 최종 산출물과 완료 조건

다음을 제공하라.

- 공통 대시보드 `validator/`와 실행 가능한 전체 소스
- 단독 실행용 정적 생성물 `tmp/build/test-site-N/` (Git 제외)
- 보고서·스크린샷은 `tmp/verification/`에 생성하고 Git에는 최신 검증 요약만 보관
- `reference/ground-truth.json`
- `README.md`: 실행·시험·배포 방법
- `REQUIREMENTS.md`: 모집요강과 구현의 대응, 자체 가정
- `VERIFICATION.md`: 실제 검증 결과와 남은 한계

문서에는 페이지 수, 정답 요소 수, 기법별 기대 건수를 구분해 기록한다. 권장 viewport, 동적 요소 대기, 탐색 범위와 종료 조건도 명시한다.

내부 링크, 검색·페이지네이션, 동적 요소, iframe, 결과 비교, 데스크톱·모바일 화면을 실제로 확인하라.

최종 답변에는 시작 URL, 검증실 URL, 산출물 위치, 핵심 검증 결과를 제시하라. 실행·검증·온라인 배포 중 완료하지 못한 부분은 명확히 구분해서 설명하라.
